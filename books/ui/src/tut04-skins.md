# Skins and Themes

This is the chapter the book is named for. The Bazaar's five gray rectangles become a
market stall you can almost smell — framed in sun-bleached wood by day and lacquered indigo
by night — and the swap between the two is a single keystroke, live, with nothing
recompiled and no layout touched. By the end you'll hold the two ideas this book has been
building toward: a **skin** is just data on widgets, and a **theme** is just a system that
asserts one skin over another.

Fulcrum has no theme engine, no style sheets, no cascade. That's not a gap you're working
around; it's the design you're about to exploit. Styling lives in ordinary component
fields, so *everything you already know about driving components applies to restyling
them.*

## The idea, before the code

A panel has three styling fields: `color`, `image`, and `nine_slice`. So far you've used
`color` alone — a flat rectangle. Give it an `image` and the texture stretches across the
panel. Add `nine_slice` and the stretch gets smart:

```text
+--------+-----------------+--------+
| corner |  edge (stretch) | corner |     the frame texture is cut into 9 pieces
+--------+-----------------+--------+     by 4 margins: [left, top, right, bottom],
| edge   | center          | edge   |     measured in TEXTURE pixels.
| (str.) | (stretches both)| (str.) |
+--------+-----------------+--------+     corners: never scaled — pixel-perfect.
| corner |  edge (stretch) | corner |     edges: stretch along their run.
+--------+-----------------+--------+     center: stretches both ways.
```

One 24x24 texture with 8px margins can therefore dress a 92x32 gold panel and a 242x50
counter without a corner ever distorting. Edges *stretch* (they don't tile), so frame art
wants stretch-safe edges: solid runs, not patterns. The Bazaar's frames were generated by
`tools/gen_bazaar_art.py` — a chunky border, studded corners, dark center — and everything
draws with nearest-neighbor sampling, so pixel art stays crisp at any panel size.

## Step 1 — dress the panels

All in `assets/ui/hud.ui.ron`, all live — keep the game running while you do this. Every
panel gains the same two fields, and its `color` changes job from *being* the paint to
*tinting* it. The gold panel, dressed:

```ron
Node(anchor: TopLeft, offset: (4, 4), size: Px((92, 32)), stack: Vertical(2),
    kind: Panel(color: (r: 1.0, g: 1.0, b: 1.0, a: 1.0),
        image: "ui/day_frame.png", nine_slice: (8, 8, 8, 8)),
    ...
```

Save, and the panel is wearing wood. Two syntax landmines, defused:

> **Don't write `Some(...)`.** `image` and `nine_slice` are optional fields, but the format
> uses RON's implicit-`Some` extension: write the value bare, exactly as above.
>
> **Margins are a tuple, not a list.** `nine_slice: (8, 8, 8, 8)` — parentheses. The order
> is `(left, top, right, bottom)`, in texture pixels. A margin pair that meets or crosses
> (left + right ≥ texture width) makes that slice zero-wide and it's skipped, which is
> also your degenerate-panel safety net: a panel *smaller* than its margins draws only what
> fits.

Dress the other four panels identically (queue, counter, pause, summary — same texture,
same margins). Then give the serve buttons their day colors, because flat default gray
under a wooden frame looks like a spreadsheet at a renaissance faire:

```ron
Node(id: "serve_figs", size: Px((72, 18)), kind: Button(text: "Figs 3g", text_size: 8, style: (
    normal: (r: 0.45, g: 0.29, b: 0.15, a: 1.0),
    hover: (r: 0.56, g: 0.38, b: 0.20, a: 1.0),
    pressed: (r: 0.33, g: 0.21, b: 0.11, a: 1.0),
))),
```

A `ButtonStyle` is three flat colors, one per interaction state. Buttons cannot wear
textures — no image, no nine-slice, caption always white and centered. That's a deliberate
floor under the widget set: a button is a colored rect that reports clicks, and richer
looks are built by *composition* (the icon column from chapter 3 is exactly that pattern).

While everything's live, play: try margins of `(4, 4, 4, 4)` and watch the border thin;
try `(12, 12, 12, 12)` on the little gold panel and watch the center pinch to nothing;
tint a panel `(r: 1.0, g: 0.6, b: 0.6, a: 1.0)` and see the texture blush. The
edit-save-look loop *is* the skinning workflow — this page is the last time the book will
mention it, because from here on you'll just do it without thinking.

## Step 2 — a second skin

One skin is decoration. Two skins force the real question: *where does the choice live?*
The answer is a plain struct in `src/main.rs` — presentation code, because a skin is
cosmetic:

```rust,ignore
/// A skin: one nine-slice frame texture plus the colors that go with it. Swapping the
/// active skin restyles every panel and button in place — the layout never changes.
struct Skin {
    frame: &'static str,
    panel_tint: Color,
    buttons: ButtonStyle,
    sky: Color,
}

const SKINS: [Skin; 2] = [
    // Day market: sun-bleached wood and parchment.
    Skin {
        frame: "ui/day_frame.png",
        panel_tint: Color::rgb(1.0, 1.0, 1.0),
        buttons: ButtonStyle {
            normal: Color::rgb(0.45, 0.29, 0.15),
            hover: Color::rgb(0.56, 0.38, 0.20),
            pressed: Color::rgb(0.33, 0.21, 0.11),
        },
        sky: Color::rgb(0.46, 0.65, 0.75),
    },
    // Night market: lacquer, indigo, and brass.
    Skin {
        frame: "ui/night_frame.png",
        panel_tint: Color::rgb(0.85, 0.87, 1.0),
        buttons: ButtonStyle {
            normal: Color::rgb(0.20, 0.22, 0.42),
            hover: Color::rgb(0.28, 0.31, 0.55),
            pressed: Color::rgb(0.13, 0.14, 0.30),
        },
        sky: Color::rgb(0.09, 0.10, 0.22),
    },
];

/// Which skin is active. Cosmetic state, so it lives in the binary, not the sim.
#[derive(Resource, Default)]
struct ThemeIndex(usize);
```

The night frame is a sibling texture with identical margins — same bones, different
clothes. Sharing margins across skins isn't required, but it keeps skins freely swappable:
the layout file's `nine_slice` stays true for all of them.

## Step 3 — the theme system

Two frame systems. First, the input:

```rust,ignore
/// T cycles the skin. Frame-level edge latch: `Input` state only changes per tick, and a
/// fast monitor runs several frames per tick — without the latch, one press could cycle
/// the theme two or three times.
fn swap_theme(input: Res<Input>, mut theme: ResMut<ThemeIndex>, mut was_down: Local<bool>) {
    let down = input.pressed(Key::T);
    if down && !*was_down {
        theme.0 = (theme.0 + 1) % SKINS.len();
    }
    *was_down = down;
}
```

> **Toolbox — the frame-edge latch:** `input.just_pressed` is a *tick*-level edge; frame
> systems can see the same tick several times. The `Local<bool>` latch is the standard
> frame-side edge detector — the same pattern the dungeon uses for its inventory key.
> (Why is theme input a frame system at all? Because the theme is cosmetic. Sim systems
> get replayed; putting the skin in the replay would mean a recorded day *forces* your
> colors. Gameplay reads input in the sim; cosmetics read input in frames.)

Then the system that earns the chapter its title:

```rust,ignore
/// Assert the active skin onto the tree, every frame. Idempotent on purpose: a hot reload
/// respawns the layout with its authored (day) styling, and this system re-themes the new
/// tree the same frame. Only panels that already wear a frame are restyled — plain color
/// panels keep whatever the layout says.
fn apply_theme(
    theme: Res<ThemeIndex>,
    mut assets: AssetLoader,
    mut config: ResMut<FulcrumConfig>,
    mut panels: Query<&mut UiPanel>,
    mut buttons: Query<&mut UiButton>,
) {
    let skin = &SKINS[theme.0];
    let frame = assets.load(skin.frame);
    for mut panel in &mut panels {
        if panel.image.is_some() && panel.image != Some(frame) {
            panel.image = Some(frame);
        }
        if panel.image.is_some() && panel.color != skin.panel_tint {
            panel.color = skin.panel_tint;
        }
    }
    for mut button in &mut buttons {
        if button.style.normal != skin.buttons.normal {
            button.style = skin.buttons;
        }
    }
    if config.clear_color != skin.sky {
        config.clear_color = skin.sky;
    }
}
```

Read it slowly — it's the whole theming philosophy in twenty lines:

> **Toolbox — widgets are just components:** `Query<&mut UiPanel>` is the escape hatch
> `UiQuery` doesn't need to provide. Panels, labels, and buttons are ordinary components on
> ordinary entities; anything the loader can set, a system can overwrite. `AssetLoader::load`
> is deduplicated by path, so calling it every frame costs a hash lookup, not a disk read.
>
> **Toolbox — assert, don't transition:** the system doesn't react to theme *changes* — it
> makes the world match the theme, every frame, and writes only when something differs.
> That shrug-idempotence buys two behaviors for free: the theme applies on the very first
> frame (no special startup pass), and it survives hot reload (the respawned tree wears
> day styling for exactly one frame — this system re-dresses it before you see it).
> Chapter 2 called this pattern out for labels; it was never really about labels.
>
> **Toolbox — `FulcrumConfig` is live:** the renderer reads `clear_color` from the config
> *resource* every frame, so the sky is themable too. Day panels on a night sky look
> wrong in a way no one can name; matching the backdrop is half of what makes a "theme"
> read as one.

Register both (`.add_frame_system(swap_theme)`, `.add_frame_system(apply_theme)`, plus
`.insert_resource(ThemeIndex::default())`), add the T hint to the corner label in the
layout, and:

```text
cargo run -p my-bazaar
```

Press T. The whole market slides into night — frames, buttons, sky — mid-day, mid-queue,
without a hitch in the sim. Press it again. Then the compound trick: switch to night, edit
`hud.ui.ron` (nudge a panel), save. Hot reload rebuilds the tree from a file that says
*day*... and you never see it, because `apply_theme` re-asserts night on the same frame.
Data-driven layout and code-driven theming, refusing to fight.

## Checkpoint

Your crate should now match `games/bazaar` — the shipped game, file for file:

```text
cargo run -p bazaar
```

New vocabulary:

| Term | What it is |
| --- | --- |
| nine-slice | 4 margins cutting a texture into 9 pieces: corners exact, rest stretches |
| margins | `(left, top, right, bottom)` in texture pixels |
| tint | `UiPanel::color`'s job once an `image` is set (white = untinted) |
| skin | one coherent set of styling data: textures + colors |
| theme | the code that asserts a chosen skin onto live widgets |

## Exercises

1. **The dawn market.** Add a third `Skin`. You can reuse `day_frame.png` with a rosy
   `panel_tint` and a pink sky — a tint-only skin is legitimate and artists lean on it
   constantly (one texture, many moods). Cycle order matters now: does T feel right going
   day → night → dawn?
2. **House colors.** Give each serve button its *ware's* color instead of one shared brown
   — extend `Skin` with `buttons: [ButtonStyle; 3]` and match them up by id in
   `apply_theme` (you'll need `Query<(&UiId, &mut UiButton)>`). The moment you need
   per-widget styling, the id is how a theme addresses a widget.
3. **Dusk fades in (harder).** Make the swap a two-second crossfade: keep `from: usize,
   progress: f32` in a resource, advance `progress` with `time.frame_delta`, and have
   `apply_theme` write per-channel lerps of the two skins' colors. The frame *texture* can't
   crossfade (it's a swap — pick the halfway point), but tint, buttons, and sky can. Notice
   you changed nothing outside presentation: the sim never learns the sun is setting.

One promise left from the introduction: that all of this — layout, clicks, menus, the whole
shopping day — is *provable* without a window. That's next, and it's shorter than you'd
guess, because you've already done the hard part by keeping the UI honest about what it is.
